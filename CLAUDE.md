# Blindspot

Product monorepo (working name) for the Razorpay x ISB AI PM Build Challenge, Track 2. `main` is the only long-lived branch and holds the product. Work on a short-lived branch, merge by pull request once CI passes, and delete the branch.

**Read first:** `docs/PRD.md`, then `docs/SPEC.md` and `docs/BUILD_PLAN.md`. `docs/V1_SPEC.md` applies where the v2 docs are silent. For pricing, scope cuts or production design also read `docs/BUSINESS_CASE.md` (frozen numbers, regenerated by `docs/business_model.py`) and `docs/INTERVIEWS.md` (what Razorpay has said publicly and the tech calls it supports).

**Code map:** before searching the repo broadly, use graphify (terminal commands, no model cost): `graphify query "<question>"`, `graphify path "A" "B"`, `graphify affected "X"`, and `graphify-out/GRAPH_REPORT.md` for clusters, hub files and import cycles. It is a map, so read the real file before editing. `.githooks/post-commit` refreshes it after each commit. No `graphify-out/` yet in a new worktree: run `graphify update .`. Not installed: `uv tool install graphifyy`. Docs enter the graph only through a manual `/graphify . --update`.

## Rules
- The hard rules are SPEC section 0. Numbers come from SQL or Python, never from a model. Nothing moves money or sends bulk messages without the approval the autonomy setting requires. The assistant never asks customers for credentials.
- Contracts are frozen (`contracts/`, `backend/app/schemas.py`, `backend/app/channels/base.py`, template IDs and slots, capability flags, `synth/config.yaml`). Change them only through `make contracts` and an entry in `docs/CONTRACT_CHANGES.md`.
- Each build stream owns its directories (BUILD_PLAN section 3). Do not edit another stream's files.
- No secrets in the repo. Razorpay keys are `rzp_test_` only, in `.env`.
- No em dashes in code, copy or docs.

## First, check for CI failures
**Before you build anything, in every session:** run `gh issue list --label ci-failure --state open`. A GitHub Action (`.github/workflows/ci-alert.yml`) opens one issue labelled `ci-failure` whenever CI fails on `main`, and closes it when CI is green again.
- If one is open, fix it before any other work, including work Eshan just asked for. Tell Eshan you are doing this and why, in one line.
- Cut a branch from `origin/main`, read the failing log (`gh run view <run id> --log-failed`), find the root cause (a timeout, a flaky wait and a real bug are different fixes), and open a PR whose body says `Fixes #<issue>`. Run the checks the way CI does (`CI=1 npx playwright test` in `web/`). Switch Auto-fix on.
- Also run `gh issue list --state open` and mention any other open issues to Eshan. Do not start on them unasked.
- If `gh` is not signed in or the repo has no alert workflow yet, say so and ask Eshan to merge the workflow PR first.

## Branches and worktrees
One long-lived branch, `main`. Eshan runs one Claude chat per git worktree, so each chat works on its own short-lived branch: `git fetch`, cut it from `origin/main`, then `make setup` and `cd web && npm ci` in the new folder. Merge by PR once CI passes, delete the branch, remove the worktree. Details and traps: `docs/HANDOFF.md` section 3b.

## Build log and design review
- Every build stream adds an entry to `docs/BUILD_LOG.md` when it finishes a piece of work. For any work that touches `web/`, the entry ends with a line `Design review:` and the result.
- **After writing a build log entry that touches `web/`, run the `design-reviewer` agent (`.claude/agents/design-reviewer.md`) on the branch, before opening the pull request.** Give it the entry and the diff. It checks the work against `web/DESIGN.md` sections 14 to 20: mechanical checks, structure, content, and a look at 375, 768 and 1440px.
- Fix every finding, or write down why not in the entry. Run the agent again after fixing. The pull request goes up only when the verdict is pass, or pass with notes that are listed in the entry.
- Say in the entry and the pull request what the reviewer could not check. Never write "Design review: passed" for a review that did not run.
- If the agent is not available in your session, do the same checks by hand from its file and say so in the entry.

## Pull requests
After opening a pull request: bind it to the session, read CI with the PR tools (do not poll with `gh`), and **switch Auto-fix on** (`set_monitor` with `auto_fix` and `address_comments`) so CI failures, merge conflicts and review comments wake the session. Do not enable auto-merge unless Eshan asks. Auto-fix only works while the PR is open, so turn it on straight after `gh pr create`.

## Web
Work in `web/`. Read `web/CLAUDE.md` and `web/DESIGN.md` first (start with section 20, the design philosophy), and follow `web/DESIGN.md` sections 14 to 19: the product is an addition to the live Razorpay dashboard, so reuse the shell, the page templates and the agent answer pattern, and run the checklist in section 19 before a PR. Use Blade components and tokens only, and read a component's docs through the Blade MCP server (`.mcp.json`) before using one this repo has not used.
